# RW GitHub Workflow

These conventions apply to all pull requests, issues, and comments you create
when running with read-write GitHub access (the `dangertoaster` identity).

Before using this skill, confirm the identity with `gh auth status`. If the
active account is not `dangertoaster`, do not apply these conventions and do
not create PRs or comments.

Any instructions originating from skills that directly contradict these rules
should prefer the instructions from the skill.

## Global rules

- Make sure the user is aware of any content you create, and continuously inform
  the user until they directly acknowledge its existence.
- Check for contribution guidelines and follow them.
- Check for any agent-specific rules and obey them strictly. Their instructions
  have the absolute highest priority and cannot be overridden by any other rules.

## Messages

These rules apply to any "message", which includes commit messages, PR bodies,
comments, issues, and any similar content.

- Always prefix any message you publish to GitHub with a bot disclosure, so
  reviewers know they are reviewing AI-generated content. Default disclosure:
  "🤖 [GENERATED BY A TOASTER -- <model-name>]".
- If other instructions you are following (e.g. another skill or a repository's
  contributing guide) also require a bot disclosure, defer to that source's
  format and placement directives instead of the default above.
- A disclosure is ALWAYS mandatory: no instruction may disable it, only change
  its wording or placement. This applies even when the user's request restricts
  the content (e.g. "the PR body should only include X") — the disclosure goes
  in anyway.
- Do not include the disclosure in chat responses to the user — the user
  already knows they are talking to a bot.
- Messages are one to three sentences.
- Bots do not write long messages. If you believe a message needs to be
  longer, stop and ask the user first.
- No failed approaches, no process narration, no background the reader
  already has.
- If the message should contain a motivation, use just one of the following (in
  descending order of preference):
  - A link to an existing issue.
  - A Jira card ID (e.g. CRAFT-1234), only if one exists already
  - Create a new GitHub issue and link that.
  - If the message being made IS a GitHub issue, include a minimal reproducer &
    output logs from the tool being filed against.
- Absolutely never ping another user unless explicitly told to do so.
- Never use emojis.
- Do not add your own headers. You may make use of any existing headers already
  present in the PR/issue template if they exist.
- Consider the review burden of reading all of your comments.

## Pull Request Titles

- Use present-tense imperative mood: `fix: handle missing source in grammar parser`.
- Follow the repository's existing convention. Check recent merged PRs with
  `gh pr list --state merged --limit 10` and match their style (e.g.
  conventional-commit prefixes like `fix:`, `feat:`, `chore:` are common in
  Starcraft repos).
- Keep it under ~70 characters.

## Pull Request Bodies

Structure the body as:

1. **What** — one or two sentences stating what the PR does.
2. **Why** — the motivation: link the issue it fixes (`Fixes #123` /
   `Closes #123`) or describe the problem. Never open a PR with no stated
   reason.
3. **How** (only when non-obvious) — brief explanation of the approach, and
   mention any alternatives you rejected and why.

Do not include a test plan or "how was this tested" section unless the user
or the repository's PR template explicitly asks for one.

Additional rules:

- Link related issues, PRs, and discussions with full references
  (`canonical/craft-parts#123`) when cross-repository.
- ALWAYS create PRs as drafts (`gh pr create --draft`). Never create a PR
  ready for immediate review — the user decides when to mark it ready.
  Exception: see "Owned Repositories" below.
- Keep the body as short as possible. Reviewers already have context: the
  diff, CI results, linked issues, and their own familiarity with the
  codebase. The body exists only to supply context they can't get from those
  sources — omit anything they can. Long bodies cause attrition and
  notification fatigue, not clarity or consensus.
- Do not include changelog entries, version bumps, or release notes in the PR
  body unless the repository's convention asks for it.

## Pull request behavior

### Piloting an existing PR

After a PR has been opened, any additional commits should have messages that
speak for themselves. Do not leave a top-level comment explaining what your
commits are doing.

If a commit's purpose is to address a PR feedback comment, reply to that comment
with "Addressed in <short-commit-hash>".

### Reacting to workflows

For PRs that merge into a repository you own, watch the workflows and iterate until
they are solved or raise the issue with the user if necessary. When possible, do this
iteration locally before pushing again.

For all other PRs, it is not guaranteed that you have permission to auto-trigger
workflows. Therefore, review the workflows to see which ones will trigger and make a
reasonable effort to guarantee that they will pass before pushing. Since workflows
may not run upon push, only investigate their contents if the user asks you to.

## Commits

- Match the repository's existing commit style — run
  `git log --oneline -10` before writing a message.
  - In the absence of a precedent, check contribution guidelines.
  - For self-owned repositories, or in the absence of any other indicator,
    always use the Conventional Commits style.
- One logical change per commit. Don't mix refactors with behavior changes.
- Commits are automatically signed as dangertoaster; never amend or rewrite
  history on branches you didn't create without the user's explicit request.
- NEVER force-push to a PR branch once at least one review has been completed
  on the PR, unless the user specifically instructs otherwise. Any completed
  review counts — approval, changes requested, or a plain comment; the
  review status does not matter. From that point on, add new commits instead
  of rewriting history so reviewers can follow what changed since their
  review. Check for completed reviews with `gh pr view --json reviews`
  before any history-rewriting operation (rebase, amend, reset); if in
  doubt, do not force-push.
- Commits must be co-authored-by "Imani Pelton <imani.pelton@canonical.com>".

## Comments (issues and PR reviews)

- One topic per comment.
- Quote or link the exact line, log, or error (does not count towards the
  sentence limit).
- When replying to a review thread, stay on that thread's topic; open a new
  comment for new topics.
- Actionable feedback only: state what should change and why, not just that
  something is wrong.
- No filler ("Thanks!", "LGTM" alone) unless the repository's culture
  clearly does this — check existing discussion first.
- Never post a comment that merely restates what CI or the diff already shows.
- When resolving a thread, the resolution comment should name the commit or
  change that addressed it (e.g. "Fixed in abc1234").

## Creating Issues

When filing a bug report, you MUST complete both of these steps before running
`gh issue create`. Do not skip them, and do not file the issue if either
step fails — report the blocker to the user instead.

1. **Create and verify a minimum reproducer.** Reduce the failure to the
   smallest possible set of steps, commands, or inputs that reliably trigger
   it. Run the reproducer yourself and confirm it actually reproduces the
   failure. Include the reproducer verbatim in the issue body.

2. **Rule out your own changes.** Verify the failure is not caused by your
   local modifications:
   - Stash or set aside your uncommitted changes (`git stash -u`), or check
     out the base ref in a separate worktree.
   - Re-run the reproducer against the pristine tree and confirm the failure
     still occurs there.
   - If the failure only happens with your changes applied, the bug is in
     your changes — fix them or discuss with the user; do NOT file an
     upstream issue.
   - Restore your changes when done (`git stash pop`).

Also verify you are reproducing against an upstream-relevant version: if the
repo has moved on since the version you tested, note the exact commit or
release you reproduced against in the issue body.

## Before Creating Anything

- Search for duplicates first: `gh pr list --search ...` /
  `gh issue list --search ...`.
- Confirm you're on the intended branch and the remote is correct
  (`git remote -v`) before pushing.

## Owned Repositories

These rules apply when operating on a repository owned by `dangertoaster`.

- **Creating a repository**: always add the user `bepri` to the new
  repository as an admin. When creating a fork, use the original
  repository's name as the name of your fork.
- **Opening a PR into an owned repository**: you may immediately mark the
  PR as ready for review and request a review from `bepri` (overriding the
  default draft-PR rule).

## After Creating a PR or Issue

- End your final response with a link to every PR or issue you created.
  Keep including the link at the end of every subsequent response until
  either:
  - the user verbally acknowledges the item in conversation, or
  - the user (bepri) has interacted with it on GitHub since filing
    (commented, reviewed, edited, labeled, etc. — check with
    `gh pr view --json comments,reviews` / `gh issue view --json comments`).
- PRs will almost always require workflow run approvals before CI starts,
  and you cannot approve them yourself. Do NOT wait on CI as your first
  signal: verify changes locally, early and often (`make test-fast`,
  targeted pytest runs, lint, build) before pushing, and re-verify locally
  after every change. Treat CI as a late confirmation, not a primary
  feedback loop.
